# Staff screens — rules
- Statement groups reuse account_groups and direct accounts.group_id membership under a presentation-only root; shared directory queries and membership helpers filter every report, and assignment edits retain existing setup/accounts permissions without posting money.
- Cash receipt, payment and deposit screens derive their operation from the `kind` search value with no in-screen type toggle, so each document item stays independent.
- Shared FormCard confirms writes by default; native forms and direct write actions explicitly confirm at the user action boundary. Retain existing detailed confirmations without doubling them; cancellation never invokes a write, queues a mutation or shows success. Automatic audit/session checks and already-confirmed offline replay do not prompt again.
- Transfer reference directories (countries, governorates, areas, transfer purposes, blacklist) are edited only from the transfer-setup screen and picked in the transfer form; a blacklist hit raises a warning but never blocks saving — the owner confirmed this: warn and still save, because refusing a customer is a compliance rule the owner has not asked to enforce.
- Outgoing (قبض) and incoming (توريد) transfers open as separate screens from their own home tiles via the `dir` search value, with no in-screen direction toggle, so staff never mix the two directions.
- Screens stay in their empty state with an explicit note until the real chart-of-accounts coding is known; invented figures would silently disagree with the existing system.
- Transfer reports, statements and totals share one read-only screen (`/transfer-reports?r=<id>`) whose report list is the only registry, and the pending pay/export lists are `view=` modes of the transfers screen, so every report reads the same posted transfers and no report posts money.
- Buy/sell totals and reports share one read-only screen (`/exchange-reports?r=<id>`) whose report list is the only registry; it reads posted buy/sell rows and never posts money.
- User-monitoring reports are read-only `r=` modes of the admin-only activity screen (`/activity?r=<id>`), with the report list in `src/lib/user-monitor.ts` as the only registry, so monitoring never adds a screen permission or touches records.
- Group and per-employee permissions are edited only on `/permissions`, a tree whose sections come from `src/lib/permission-tree.ts` and must list every screen in `SCREENS` exactly once; saving upserts one row per changed screen into the group or employee table, and the employee baseline is computed by the same pure helpers that mirror the database check.
